# AML Network Graph Engine

**Real-Time Financial Fraud Detection & AML Network Graph Engine**

A research/prototype system that detects Anti-Money Laundering (AML) patterns in financial transaction streams using a multi-stage pipeline: SQL behavioural aggregation, NetworkX graph analytics, and Isolation Forest anomaly detection, all served through a FastAPI WebSocket stream and a Streamlit compliance dashboard.

> ⚠️ **This is a synthetic-data research prototype, not a production compliance system.** All transactions are generated by a reproducible simulator. The system has not been validated on real financial data and must not be used for regulatory compliance.

---

## Problem Statement

Traditional rule-based AML systems flag individual transactions that exceed fixed thresholds (e.g. `amount < $10,000`). This misses coordinated behavioural patterns such as:

- **Structuring (smurfing):** Multiple sub-threshold transactions that collectively exceed a reporting limit.
- **Layering:** Multi-hop fund movement through intermediaries to obscure origin.
- **Circular flows:** Funds returning to an originating entity through a transaction cycle.
- **Velocity bursts:** Unusually high transaction frequency in short windows.

This project addresses all four patterns using a combination of SQL aggregation, graph topology analysis, and unsupervised machine learning.

## Data Flow in Detail

### SQL Structuring Detection

Structuring is detected using SQL aggregation — **not** by checking `amount < threshold` on individual transactions:

```sql
SELECT t1.tx_id, COUNT(t2.tx_id) AS window_count, SUM(t2.amount) AS window_sum
FROM   transactions t1
JOIN   transactions t2
       ON  t2.source_entity = t1.source_entity
       AND t2.amount        < 10000
       AND t2.timestamp    >= datetime(t1.timestamp, '-60 minutes')
       AND t2.timestamp    <= t1.timestamp
WHERE  t1.amount < 10000
GROUP  BY t1.tx_id
HAVING COUNT(t2.tx_id) >= 3
```

This identifies entities with **≥3 sub-threshold transactions aggregating to a suspicious total within a 60-minute window** — the coordinated behaviour, not individual amounts.

A triggered alert reads:
```
STRUCTURING: 7 sub-threshold transactions totalling $67,420
(avg $9,631) within 60 min window
```

### Graph Construction

The directed transaction graph `source_entity → dest_entity` is maintained as a rolling 1-hour window. Each edge carries `weight` (total amount), `tx_count`, and `avg_amount`.

**Betweenness Centrality** — identifies intermediary entities through which many shortest paths pass, revealing bridge nodes used for layering. Computed with k-sample approximation when the graph exceeds 50 nodes.

**Eigenvector Centrality** — computed on the undirected projection via NumPy eigensolver (always converges; avoids power-iteration divergence on sparse directed graphs). Identifies entities connected to other influential entities.

**Community Detection** — greedy modularity communities on the undirected projection. Tightly coupled communities may indicate coordinated rings.

**Cycle Detection** — SCC decomposition (Tarjan's algorithm via NetworkX). Nodes in strongly connected components of size ≥ 2 participate in circular flows. Avoids the O(V+E+C) cost of `simple_cycles` on dense graphs.

**Multi-hop Analysis** — `shortest_path_length(source, dest)` gives the hop count between transaction endpoints. Normalised to [0, 1] over a maximum depth of 5.

**Rolling-window correctness** — when a transaction expires, its contribution is decremented from the edge weight. The edge is only removed when zero active transactions remain in the window. Out-of-order timestamps (e.g. from batch evaluation) are handled correctly by scanning the full expiry queue.

### Composite Risk Score

```
composite_risk = 0.30 × IF_score
              + 0.25 × graph_score
              + 0.20 × structuring_score
              + 0.10 × velocity_score
              + 0.10 × circular_score
              + 0.05 × high_risk_jx_score
```

Weights are defined in `backend/config.py` and sum to 1.0. Classification thresholds:

| Label | Threshold |
|---|---|
| CRITICAL | ≥ 0.80 |
| HIGH | ≥ 0.60 |
| MEDIUM | ≥ 0.40 |
| LOW | < 0.40 |

### Real-Time Architecture

A single central processing loop in `backend/streaming.py` generates and processes every transaction. All connected WebSocket clients receive identical broadcast records from a shared queue — there is no separate generator per client.

```

```

## Evaluation Methodology

**Protocol (60 / 20 / 20 split, time-ordered):**

1. Generate 20,000 synthetic transactions (seed=42).
2. Train Isolation Forest on the first 60% — no labels used as features.
3. Select classification threshold on the 20% validation split only.
4. Report final metrics on the held-out 20% test set — never seen during tuning.

**Contamination:** Fixed at 0.08 (realistic AML anomaly rate) rather than the synthetic dataset's label rate (~45%), which would be unrealistic and would harm IF training.

**No leakage:** `pattern_type` is used only to compute evaluation metrics after prediction. It is not passed to any model feature.

**Reproducible with:**
```bash
python scripts/evaluate_model.py --transactions 20000 --seed 42
```

### Actual Evaluation Results (seed=42, 20,000 transactions)

| Metric | F1-optimal threshold (0.50) | Precision-optimal threshold (0.60) |
|---|---|---|
| **Precision** | **86.39%** | **100.00%** |
| **Recall** | **53.82%** | **31.26%** |
| **F1** | **66.33%** | **47.64%** |
| Accuracy | 75.35% | — |
| TP | 971 | 564 |
| FP | 153 | 0 |
| TN | 2,043 | 2,196 |
| FN | 833 | 1,240 |

Both thresholds are selected on the validation set and locked before the test set is evaluated.

**Score overlap:** Normal transactions have a p99 composite score of 0.56; suspicious transactions have a p10 of 0.43. This 13-percentile overlap explains the recall ceiling — the distributions are not perfectly separable with the current feature set.

## SQL Performance Benchmark

Compares three structuring-detection implementations on identical data:

1. **Naive Python** — O(N²) nested loops, no sorting.
2. **Optimised Python** — O(N log N) sorted sliding-window deque.
3. **SQL indexed** — self-join `GROUP BY / HAVING` on indexed columns.

**Reproducible with:**
```bash
python scripts/benchmark_sql.py --full --seed 42
```

### Actual Benchmark Results (seed=42)

| Dataset | Naive Python | Optimised Python | SQL (indexed) | Naive→SQL | Opt→SQL |
|---|---|---|---|---|---|
| 100,000 | ~0.92s | ~0.26s | ~0.24s | ~74% | ~8% |
| 250,000 | ~4.5s | ~0.73s | ~0.75s | ~83% | ~−3% |
| **500,000** | **~17.1s** | **~1.50s** | **~1.81s** | **~89%** | **~−20%** |

**Key finding:** SQL outperforms naïve O(N²) Python by ~82–89% at scale. Against well-written O(N log N) Python, SQL performance is comparable — SQLite's in-process overhead eliminates the server-side SQL advantage that would appear with PostgreSQL. The SQL approach's value is in **declarative correctness**, **index exploitation**, and **maintainability**, not raw speed vs optimised Python.

## Financial Analytics Layer

On top of the real-time AML engine above, this project also includes a
batch **financial data analytics / BI layer** — the same architecture a
compliance-analytics or BI analyst role would expect, built around the
same `transactions`/`alerts` data the AML engine already produces
rather than a separate mock dataset. Full details, including the exact
business-question-to-query mapping and known limitations, are in
`docs/analytics.md`, `docs/data_quality.md`, and `docs/powerbi.md`.

### Data Quality

`backend/data_quality.py` runs 14 deterministic, read-only SQL checks
against `transactions`/`alerts` (nulls, duplicates, invalid amounts,
invalid currency/jurisdiction codes, self-transactions, bad timestamps,
invalid pattern types, orphaned alerts, blank entity IDs, and
statistical outliers) and writes structured results to a
`data_quality_results` table and `data_quality_report.json`. Checks
never delete data — they only report. See `docs/data_quality.md` for
the full check list, including a real bug the framework caught on
itself during development (an incorrect assumed set of `pattern_type`
values that would have wrongly failed ~36% of legitimate transactions).

### Advanced SQL Analytics

`sql/analytics/` contains 12 files covering 19 distinct, business-
question-driven queries against the real schema — CTEs, `RANK()`,
`DENSE_RANK()`, `ROW_NUMBER()`, `LAG()`/`LEAD()`, rolling `SUM()`/`AVG()
OVER()`, `NTILE()` quartile segmentation, correlated subqueries, and
`CASE`-based classification. Every query answers one of the 16 business
questions listed in `docs/analytics.md` (e.g. "which entities have
repeated structuring alerts," "which entities act as major
intermediaries," "what percentage of transaction value is flagged") —
none were added just to demonstrate a syntax feature.

### Analytics Pipeline & KPI Layer

```bash
python scripts/build_analytics_dataset.py
```

Runs the full pipeline end to end: generates a reproducible seeded
sample (5,000 transactions, seed=42) through the **real** processing
pipeline (`backend.streaming._process_transaction` — the same function
the live FastAPI service uses, not a shortcut), runs the data-quality
framework, executes every analytics query, computes the documented KPI
layer (16 KPIs — total/median transaction value, suspicious transaction
rate, flagged value %, structuring alert count, circular-flow entity
count, high-risk jurisdiction exposure, and more — see
`docs/analytics.md` for exact definitions), and exports 19 Power-BI-
ready CSVs plus a KPI summary to `exports/`. A small version of this
export (~160KB) is committed as a reproducible fixture; the database
itself is not (see `.gitignore`).

### Power BI Integration

`docs/powerbi.md` specifies which exported CSVs to import, the
recommended relationships between them, five dashboard pages
(Executive Overview, Risk Analytics, Entity & Network Risk, Temporal &
Jurisdiction Analysis, Data Quality), and which calculations belong in
SQL vs. DAX. `docs/dax_measures.md` has the actual DAX syntax for 16
measures. **No `.pbix` file is included** — Power BI Desktop was not
available in the build environment, so this is the complete dataset +
schema + DAX specification a Power BI build would use, not a claim that
a working `.pbix` already exists.

RiskWeights(
    isolation_forest = 0.30,
    graph_score      = 0.25,
    structuring      = 0.20,
    velocity         = 0.10,
    circular_flow    = 0.10,
    high_risk_jx     = 0.05,

IFConfig(n_estimators=200, contamination=0.08, random_state=42)

# Structuring detection
AMLRuleConfig(
    structuring_threshold   = 10_000.0,
    structuring_window_minutes = 60,
    structuring_min_count   = 3,
)

## Limitations

1. **Synthetic data only.** The generator is calibrated to produce detectable patterns; real transaction distributions will differ.
2. **Recall ceiling (~54%).** Score distributions overlap significantly at the F1-optimal threshold. Higher precision (~100%) is achievable at threshold 0.60 but reduces recall to ~31%.
3. **SQLite in-process.** The SQL performance advantage is smaller than it would be with a client-server database (PostgreSQL) due to the absence of network latency in the baseline.
4. **Graph window.** The 1-hour rolling window may miss long-horizon layering patterns (days/weeks) seen in real AML cases.
5. **Unsupervised only.** Isolation Forest has no concept of labelled fraud. A labelled dataset would allow supervised classification with likely higher recall.
6. **Single-process streaming.** The current architecture runs in one Python process. Production deployments would use Kafka, Flink, or similar stream-processing infrastructure.
